# 1. نبذة عن المشروع

المشروع عبارة عن خط معالجة بيانات هجين مخصص لبيانات الطلبات الموجودة داخل ملفات CSV.

الفكرة الأساسية هي استخدام أكثر من طريقة لمعالجة البيانات بدل الاعتماد على محرك واحد فقط.

يقوم النظام باختيار طريقة المعالجة المناسبة، ثم يمرر البيانات إلى مراحل التحميل والتحقق والتنظيف والتصنيف.

بعد قراءة الملف، يتم إنشاء معرف تشغيل خاص يسمى:

`text

3. اختيار طريقة المعالجة
يحتوي المشروع على محركين لمعالجة البيانات:
Python Batch
يتم استخدام Python لقراءة البيانات وإدخالها إلى MongoDB على شكل دفعات.
يتم تجميع عدد من السجلات داخل Batch، وبعد ذلك يتم إرسالها إلى MongoDB باستخدام:
insert_many()
ويتم حساب عدد السجلات والوقت ومعدل المعالجة.
PySpark
يتم استخدام Apache PySpark لمعالجة البيانات باستخدام DataFrame وPartitions.
يقوم المحرك بقراءة ملف CSV ثم تقسيم البيانات إلى أجزاء، وبعد ذلك يتم إرسال البيانات إلى MongoDB.
كما يقوم Spark بحساب:
Partitions
source_row_number
عدد السجلات
زمن التنفيذ
Throughput

4. طبقة البيانات الخام
قبل تنفيذ أي عملية تنظيف أو تعديل، يتم حفظ البيانات في:
orders_raw
وتحتوي السجلات على معلومات تساعد في تتبع مصدرها.
مثال:
{
    "run_id": "12345",
    "source_file": "orders.csv",
    "source_row_number": 10,
    "ingested_at": "2025-01-31T10:30:00",
    "engine_used": "python_batch",
    "raw_record": {
        "order_id": "ORD-1001",
        "customer_id": "CUST-500"
    }
}
وجود raw_record يسمح بالمحافظة على البيانات الأصلية قبل إجراء عمليات التحويل.

5. مرحلة تنظيف البيانات
توجد قواعد تنظيف ومعالجة البيانات داخل:
src/quality_rules.py
ومن أهم العمليات التي ينفذها النظام:
تحويل الأرقام العربية
مثال:
٥٠٠٠
تصبح:
5000
إزالة فواصل الآلاف
مثال:
5,000
تصبح:
5000
توحيد العملة
القيم المختلفة التي تشير إلى الريال اليمني يتم توحيدها إلى:
YER
معالجة الأسعار المكتوبة بالكلمات
يدعم النظام بعض القيم العربية المعروفة مثل:
ألف       → 1000
ألفان     → 2000
ألفين     → 2000
ثلاثة آلاف → 3000
أربعة آلاف → 4000
خمسة آلاف  → 5000
تنظيف رقم الهاتف
يتم إزالة بعض المسافات والرموز غير الضرورية من رقم الهاتف.
تنظيف البريد الإلكتروني
يتم إصلاح بعض الأخطاء الواضحة في البريد الإلكتروني.
مثال:
user@@mail..com
يمكن تحويله إلى:
user@mail.com
توحيد التاريخ
يتم تحويل صيغ التاريخ المختلفة إلى صيغة موحدة:
YYYY-MM-DD
مثال:
31/01/2025
تصبح:
2025-01-31
فحص items_json
يتم التحقق من أن قيمة:
items_json
تحتوي على JSON صالح.
وفي بعض الحالات البسيطة يتم إصلاح تنسيق JSON قبل استخدامه.

6. التحقق من الحقول الأساسية
يتحقق النظام من وجود بعض الحقول المهمة في الطلب، ومنها:
order_id
customer_id
order_date
items_json
مثلاً إذا لم يكن هناك order_id صالح، يتم تسجيل:
MISSING_ORDER_ID
وإذا كان customer_id مفقودًا:
MISSING_CUSTOMER_ID

7. الحالات النهائية للسجل
بعد انتهاء عملية التحقق، يتم وضع كل سجل في إحدى الحالات التالية:
✅ Valid
السجل صحيح ولا يحتاج إلى تعديل.
valid
🔧 Corrected
السجل يحتوي على مشكلة يمكن إصلاحها باستخدام قاعدة واضحة.
مثال:
٥٠٠٠
يتم تحويلها إلى:
5000
ويتم تصنيف السجل:
corrected
⚠️ Quarantined
إذا كان الخطأ جوهريًا ولا يمكن إصلاحه بأمان، لا يتم حذف السجل.
بدلًا من ذلك يتم وضعه في:
orders_quarantine

8. أسباب العزل
من الأخطاء التي يمكن أن تؤدي إلى عزل السجل:
MISSING_ORDER_ID
MISSING_CUSTOMER_ID
INVALID_IMPOSSIBLE_DATE
EMPTY_ITEMS
CORRUPTED_ITEMS_JSON
AMBIGUOUS_NEGATIVE_VALUE
MULTIPLE_CONFLICTING_ERRORS
وبذلك تظل البيانات غير الصالحة محفوظة ويمكن مراجعتها لاحقًا.

9. تتبع عمليات التصحيح
عند تعديل قيمة داخل السجل، لا يتم الاحتفاظ بالقيمة الجديدة فقط.
يتم أيضًا تسجيل تفاصيل التعديل داخل:
corrections
مثال:
{
    "field": "customer_email",
    "original_value": "user@@mail..com",
    "corrected_value": "user@mail.com",
    "rule_code": "EMAIL_REPEATED_SYMBOLS"
}
وبذلك يمكن معرفة:
اسم الحقل.
القيمة قبل التعديل.
القيمة بعد التعديل.
القاعدة التي قامت بالتصحيح.

10. تخزين النتائج
بعد انتهاء عملية التنظيف، يتم تخزين السجلات المقبولة والمصححة في:
orders_validated
بينما يتم تخزين السجلات التي لم تستطع قواعد الجودة إصلاحها في:
orders_quarantine
وبالتالي تصبح قاعدة البيانات مقسمة إلى ثلاث مراحل:
orders_raw
orders_validated
orders_quarantine

11. منع التكرار وإعادة التشغيل
يستخدم النظام:
order_id
كمفتاح للبحث عن السجل داخل orders_validated.
وتستخدم مرحلة ELT:
UpdateOne(..., upsert=True)
بحيث إذا كان السجل موجودًا يتم تحديثه، وإذا لم يكن موجودًا يتم إنشاؤه.
الهدف هو جعل إعادة تشغيل البيانات أكثر أمانًا وتقليل احتمالية إنشاء سجلات مكررة.

12. معرف عملية التشغيل

25. الخلاصة
يقدم المشروع نموذجًا لخط معالجة بيانات يمكنه التعامل مع بيانات الطلبات باستخدام أكثر من محرك معالجة، مع المحافظة على البيانات الأصلية قبل التعديل.
كما يوفر النظام آلية لتصحيح الأخطاء القابلة للإصلاح، وعزل السجلات التي تحتوي على أخطاء حرجة، وتسجيل التعديلات التي تمت على البيانات.
وفي النهاية يتم حفظ نتائج التشغيل وقياسات الأداء حتى يمكن الرجوع إليها وتحليلها.
